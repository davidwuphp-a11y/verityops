# Verification model

The supported task is one isolated order (`order-1`) for a positive integer amount in minor units. Its starting state must be paid for that amount, with zero target refunds and an open ticket. A hold is a successful business outcome when the contract calls for it.

1. **Ownership and scope.** Match the order primary key to the ticket reference and each refund's non-null order foreign key. The idempotency request key may differ between valid records. Before filtering by order, the reader looks for unassigned or dangling refunds in the authorized synthetic partition. Such a record could be an unaccounted second posting.
2. **Completeness.** In one read transaction, count the matching and other rows and read all target rows ordered by ledger ID. Validate unique IDs, matching owners, and the length against the target count. An otherwise satisfied contract with a changed other-order refund count becomes INCONCLUSIVE. Against a filtered external view these checks alone cannot establish completeness.
3. **Financial and eligibility rules.** The original paid principal must stay constant. A refund requires exactly one row for the full agreed amount; a hold requires zero. More than one row is a duplicate. On every row, approval and permission must be set, the order status sampled at submission must be paid, and the logical clock must be earlier than the deadline. Currency and external policy history are absent from this fixture.
4. **Projections and verdict.** A refund ends with refunded/closed; a hold with paid/open. Complete, valid evidence satisfying the checks yields PASS. An observed contract violation yields FAIL with issue codes. Unsupported initial state, missing evidence or an incompatible snapshot yields INCONCLUSIVE. The runner does not automatically repeat an action that raises an exception.
5. **Comparison across releases.** A regression captures the task, stimulus, observed release and required PASS. Replays select a release explicitly. A reproduced defect can therefore return FAIL with exit 1; a candidate is evaluated against the same expectation. The batch checks exact equality of original replay evidence and the first failing evidence, then checks for a passing reference.

The JSON schemas describe generated [snapshots](schemas/readback.schema.json), [regression files](schemas/regression.schema.json) and [scenario definitions](schemas/scenarios.schema.json). They document serialized output. Runtime validation and cross-field invariants live in Python; the runner accepts some minimal replay inputs using dataclass defaults. SQLite DDL is in the fixture and sandbox source.
